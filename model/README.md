# Загрузка Capibara: raw -> core

Вся реализация находится в `model/`. Исходные CSV, `raw`, скрипты проекта и SQL автора отчётов не изменяются. Сохраняется договор v1: девять таблиц `core` и два представления `mart.order_totals`, `mart.sales_items` с ранее согласованными полями.

## Запуск в Ubuntu

Из корня проекта:

```bash
cd ~/rwb_hack
sudo bash model/run.sh build
sudo bash model/run.sh check
```

`sudo` нужен в текущей Ubuntu для доступа к Docker. Если у пользователя уже есть доступ к Docker, запускайте без него. Скрипт использует работающий сервис `postgres` из существующего `docker-compose.yml`, пользователя `hack`, базу `marketplace`. Установку, запуск контейнера, загрузку или сброс `raw` он не выполняет.

Для подключения к другой PostgreSQL можно выполнить SQL напрямую:

```bash
psql -X -v ON_ERROR_STOP=1 -d marketplace -f model/build.sql
psql -X -v ON_ERROR_STOP=1 -d marketplace -f model/checks.sql
```

Параметры доступа задайте обычными средствами psql. Нужны чтение и SHARE-lock таблиц `raw`, создание/заполнение `core`, создание представлений `mart`.

## Файлы

- `build.sql` — самостоятельная SQL-сборка: проверки источника, таблицы, преобразования, загрузка, представления, проверки целостности. Один файл и одна транзакция.
- `checks.sql` — проверки конкретной исходной выгрузки и контрольных цифр. Работает в режиме `READ ONLY`.
- `raw_fingerprint.sql` — количество строк и отпечатки всех колонок каждой таблицы `raw`, включая метаданные загрузки. Только чтение.
- `run.sh` — запуск SQL через существующий Docker Compose.
- `verify.sh` — два запуска сборки, сверка результатов и доказательство неизменности источников.
- `reports/` — журналы фактических запусков и отпечатки до/после.

## Что делает сборка

1. Начинает транзакцию `REPEATABLE READ`, исключает одновременный второй запуск этой сборки и берёт SHARE-lock на источники на время загрузки.
2. Проверяет словарь категорий, зарезервированный ключ неизвестной категории, точность денег и отсутствие времени в обещанной дате доставки.
3. Создаёт согласованные таблицы, если их ещё нет. Сверяет существующие колонки, типы, обязательность и первичные ключи с договором v1. При несовпадении останавливается.
4. Очищает только девять именованных таблиц `core` и загружает их из `raw` в порядке внешних ключей. `DROP` и `CASCADE` не используются.
5. Создаёт или обновляет только два согласованных представления `mart`. Остальные объекты и файлы отчётов не затрагивает.
6. Проверяет сохранение строк, денежных сумм, статусов и уровня детализации представлений; только после этого фиксирует транзакцию.

Повторный запуск полностью обновляет данные этих девяти таблиц `core` из `raw`. Это полный пересчёт снимка, а не инкрементальная загрузка. Ручные исправления внутри этих таблиц при следующем запуске заменятся данными источника. Ошибка при запуске с `ON_ERROR_STOP=1` откатывает незавершённую транзакцию.

На время `TRUNCATE` и загрузки PostgreSQL блокирует обращения к обновляемым таблицам. Запускайте пересборку между проверками отчётов. Таймаут ожидания блокировки — 10 секунд: сборка завершится ошибкой, если таблицу надолго удерживает другое подключение.

## Преобразования

| Источник | Результат |
|---|---|
| `raw.customers.customer_unique_id` | Уникальные люди в `core.customers` |
| Все строки `raw.customers` | `core.customer_profiles` с исходным адресом профиля |
| Категории из товаров + левое соединение с переводами | `core.categories`, включая `__unknown__` и категории без перевода |
| `product_name_lenght`, `product_description_lenght` | Исправлены только имена колонок в `core`: `..._length` |
| Пустые числа, даты, идентификаторы | `NULL` после удаления пробелов; обязательные поля проверяет схема |
| Тексты отзывов | Сохраняются без обрезания содержимого; пустая строка заменяется на `NULL` |
| Денежные поля | Точный `numeric(14,2)`; значащие дробные разряды сверх двух запрещены, не округляются молча |
| Даты событий | `timestamp without time zone`, без выдуманного часового пояса |
| Обещанная дата доставки | `date`; ненулевое время в новых данных останавливает сборку для пересмотра правила |
| Заказы и отзывы | Все статусы и все записи сохраняются |

Одна строка позиции равна одной единице товара. `order_item_id` — номер позиции, не количество. Платёж не умножается на число частей рассрочки. Нулевая сумма платежа сохраняется.

Противоречия источника не исправляются автоматически: заказы без позиций, отсутствие платежа/даты вручения, несколько отзывов, события в необычном порядке сохраняются. Для доставленного заказа отсутствие позиций считается блокирующей проблемой для публикации отчётов; в текущей выгрузке таких заказов нет.

## Интерфейс для друга

Таблицы: `core.customers`, `core.customer_profiles`, `core.sellers`, `core.categories`, `core.products`, `core.orders`, `core.order_items`, `core.order_payments`, `core.order_reviews`.

**`mart.order_totals`: одна строка на любой заказ.** Есть постоянный идентификатор покупателя, статус, даты, `purchase_month`, `item_count`, `unit_count`, `product_count`, `seller_count`, `items_amount`, `freight_amount`, `order_amount`, `payment_count`, `payment_amount`, `review_count`, последний отзыв, признаки наличия данных и `is_late`.

**`mart.sales_items`: одна единица товара доставленного заказа.** Есть товар, продавец и его география, покупатель, категория, месяц оформления, `quantity = 1`, `item_amount`, `freight_amount`, `item_amount_with_freight`, срок отгрузки.

Платежи и отзывы сначала агрегируются независимо до заказа, поэтому соединения не размножают денежные суммы. Последний отзыв определяется по времени ответа, затем создания, затем идентификатору. Для неизвестной даты вручения `is_late = NULL`; просрочка сравнивает календарные даты.

Если позиций/платежей нет, их количество равно 0, а денежная сумма `NULL`. Это позволяет отличить отсутствие сведений от реального нуля.

В `build.sql` встроены общие проверки относительно `raw`, без фиксированного количества строк. `checks.sql` намеренно привязан к этому снимку: при изменении источника его ожидаемые числа нужно пересмотреть, а не подгонять загрузку.

Проверить сборку дважды и неизменность источников:

```bash
sudo bash model/verify.sh
```

Отпечатки `raw` учитывают полное содержимое всех исходных колонок и кратность строк независимо от их физического порядка. SHA-256 CSV сверяются отдельно. Журналы записываются только в `model/reports`.

## Проверка сбоев

Неверный тип, повтор первичного ключа или отсутствующая внешняя ссылка приводит к явной ошибке PostgreSQL и откату. `ON CONFLICT DO NOTHING` не применяется. Новые статусы не ограничены жёстким перечислением. Схему можно расширять только согласованно с автором отчётов.

Сборка не запускает `scripts/setup.sh` и `scripts/load_raw.py`, поскольку эти скрипты могут пересоздать исходный слой. Не используйте их для обычного обновления нашей модели.
